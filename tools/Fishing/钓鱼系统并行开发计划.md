# 拟真钓鱼系统：多会话并行开发计划

日期：2026-09-29。状态：设计计划，尚未实现或完成游戏内验证。

执行更新：A 已发布 `Contracts-v1.md`、真实接口类型与可编译骨架，自动验证和原生组件探针详见 `Integration/M0-report.md`。B–F 可依据已发布契约继续并行开发；M0 的完整玩家交互验收仍单独保留，不因接口发布而视为通过。当前里程碑状态以 `STATUS.md` 为准。

## 1. 最终目标与实现边界

在当前 ProjectZ + AEC 环境制作独立钓鱼模组，暂定目录 `ZZZ-PZAEC_Fishing`、命名空间 `PZAEC.Fishing`。完整体验必须包含：

1. 可见的鱼竿、鱼线、浮漂、鱼及水面反馈。
2. 鱼试饵、含饵、移动引起点漂、送漂、走漂、黑漂；扬竿时机影响挂钩结果。
3. 鼠标抬竿、送竿、侧向压竿，卷线和泄力操作。
4. 鱼连续数轮爆发、停歇、转向、近岸反扑，力量与体力有因果关系。
5. 持续后拉鼠标可带动人物尝试后退，负载越高越难后退；支持方向键主动走位。
6. 拉力、竿弹性、线伸长、泄力和走位共同影响结果；可能断线、脱钩和跑鱼。
7. 中鱼、遛鱼、上岸、扣饵、奖励和中途取消构成完整流程。

普通鼠标不能提供实际机械阻力。目标是通过受载后的竿响应、人物步速、竿弯、声音和适度镜头反馈形成阻力感。反馈必须与真实模拟状态一致，不额外叠加无根据的迟滞。

第一里程碑聚焦第一人称、岸钓、一根竿、一种鱼、一类鱼饵。漂亮场景、更多鱼种与多人完善在后续里程碑交付；占位模型只能用于开发验收，不能宣称为最终真实场景。

## 2. 已知环境与必须先验证的事项

已确认本机包含游戏 `7DaysToDie_Data/Managed/Assembly-CSharp.dll`、`0_TFP_Harmony`、C# 源码和既有构建脚本。`ZZZ-PZAEC_Surveillance/Source/PZAEC.Surveillance.csproj` 是 net48 项目，可作为引用结构的参考，但新项目必须自行验证编译条件。

现有模组 README 写有 V3.2；这不是对当前运行版本的独立核验。A 会话必须记录实际程序集版本、游戏版本证据和可用构建工具。

A 必须先做技术探针，不能把下列能力当作已确认：

- 当前水系统如何取得水面位置、水深和可钓区域，如何处理分块卸载。
- 如何在持有鱼竿时读取鼠标增量，并正确隔离视角、攻击、背包与菜单输入。
- 如何通过现有角色移动流程施加后退请求、速度限制和受力反馈，保留碰撞、斜坡及其他减速效果。
- 如何添加持竿、竿尖、线、浮漂的渲染对象，第一人称手部骨骼及动画是否可复用。
- 是否有可用的 Unity 编辑器及匹配版本、模型导出和 AssetBundle 构建途径。
- 物品实例、背包奖励、存档和网络扩展接口的实际行为。

关键接口失败时，写明证据和可行替代路径，由 A 更新契约。第三人称动画暂缺可以分阶段补齐；核心鼠标控竿和受力走位不可被悄悄替换成按键抽奖。

## 4. A 必须先交付的契约 v1

先创建可编译骨架及测试替身。以下是契约所需信息，不是对游戏已有 API 名称的声明；A 应把最终字段、类型、坐标规则和调用顺序写入契约文档并落实为代码。

### 数据、单位与所有权

- 全部长度用米、时间用秒、力用牛顿、角度用弧度；定义世界向上方向、竿本地轴和鼠标正负号。
- 输入：序号、采样时间、鼠标累计增量、抬竿/侧压意图、卷线、泄力、移动意图、自由观察与取消。
- 环境：玩家实际位置/速度、竿根与竿尖姿态、水面与水底采样、有效水域及障碍查询。
- 模拟输出：会话 ID、模拟 tick、阶段、鱼位置/速度/朝向/体力/爆发状态、线长/伸长/张力、竿受力、浮漂姿态、挂钩状态、失败原因。
- 移动输出：附加移动意图及负载修正；人物实际移动由游戏适配层执行，下一 tick 反馈真实位移。
- 事件：抛投、触水、试饵、含饵、有效提竿、中鱼、冲刺、泄力、松线、断线、脱钩、上岸、取消；每个事件有唯一序号，避免声音和奖励重复。
- 配置：竿、线、泄力、钩、漂、鱼参数以及输入灵敏度；明确默认值、合法范围和配置版本。

### 模块边界

- B 是鱼、线张力、竿受力与浮漂模拟的唯一写入者；不得访问背包、Unity 场景对象或输入系统。
- C 只产出操作意图及操作映射，不创建第二套张力计算，不直接修改人物坐标。
- D 消费快照与事件做表现，不自行判定中鱼、断线或生成物品。
- E 提供定义、配置加载与奖励规格，不直接结算奖励。
- F 拥有网络消息实现、校验与多人测试；A 的结算服务是奖励发放的唯一入口，单人与多人共用它。
- A 拥有游戏生命周期、环境采样、移动适配、库存事务和跨模块调用顺序。
- 物理模拟采用固定步长，初始候选为 60 Hz；渲染插值，鼠标按帧采样后正确累积到 tick。是否降至 30 Hz 由性能与稳定性测试决定。
- 核心模拟使用独立向量结构和可注入随机源，避免依赖场景才能测试。

### 状态机

`Idle → Casting → Settling → Waiting → Nibbling → BiteWindow → Hooked → Fighting → Landing → Resolved → Idle`

另有 `Cancelled`、`LineBroken`、`HookLost` 终止路径。明确每一步资源消耗、输入所有权、视觉对象清理、奖励资格与状态超时。松线过久、远离水域和鱼进入无效空间必须有有据可查的处理规则。

多人契约从第一天保留会话 ID、输入序号、tick、权威状态和结算 ID。第一里程碑先跑单机，不表示多人可直接复用而无需验证。

## 5. 各会话详细交付

### A：架构、技术风险与整合

先完成水面检测、输入接管、移动适配和简易渲染探针，再冻结契约。建立独立模组及暂存构建目录，不把不完整 DLL 安装进游戏。

主循环顺序须固定：采集输入及环境 → 操作意图 → 固定步模拟 → 移动请求 → 输出快照/事件 → 渲染；实际移动反馈进入下一步模拟，禁止重复移动。若当前游戏更新顺序需要调整，契约中说明延迟与稳定性处理。

受击、死亡、换物品、开菜单、进入载具、游泳、断线、退出存档都必须恢复输入及移动控制并释放场景对象。第一版受击直接取消钓鱼，后续再讨论保留战斗中的钓鱼状态。

背包满、重复上岸事件、扣饵后中断、保存/加载必须有明确且幂等的处理策略。第一版不保存进行中的鱼战，加载时结束会话并恢复正常控制；奖励记录需防重复结算。

### B：模拟

建立可回放的独立模拟，固定随机种子可以复现整场遛鱼。

- 鱼在有效水域活动；避免钻岸、穿底和水外冲刺。第一版复杂障碍挂线可暂不开放，但线穿过实体应有检测及明确终止/限制规则。
- 线在拉直后才产生拉力；伸长、伸长速度和阻尼共同形成张力，泄力允许出线并影响能量消耗。
- 竿具备弹性缓冲和角度限制；先选可稳定求解的简化模型，不追求全杆有限元。
- 浮漂吃口由鱼施加的牵引和浮力产生，支持小幅试探、抬升、横移和下沉；挂钩窗口与行为状态一致。
- 鱼有巡游、含饵、惊逃、冲刺、恢复、侧跑和近岸反扑状态；至少呈现三轮可区分的爆发，但不得通过固定计时无条件消耗所有体力。
- 断线同时考虑极限拉力和持续过载损伤；脱钩考虑挂钩质量与持续松线。阈值参数可调。
- 后退提高牵引与鱼冲刺提高张力遵循同一几何关系，不因“按了后退键”直接奖励进度。

必要测试：松线不应凭空出现巨大拉力；泄力能限制持续过载；鱼体力不越界；时间步变化不会造成爆炸；固定输入可复现；猛拉与缓拉有可解释的差异。

### C：操作与受力走位

默认方案：鼠标前后控制抬/送竿，左右控制侧压；按住卷线键收线，独立操作调节泄力；WASD 主动移动。具体默认键须检查现有键位冲突后确定，并提供重绑定或配置。

鼠标后拉优先抬竿；接近抬竿范围上限后，持续后拉转换为有上限的后退意图。只要鼠标停止，额外后退意图应衰减停止。不能积累无穷输入导致松手后人物仍走动。

后退速度取决于牵引方向与角色可用移动能力；鱼线松弛时不应减速，反向操作不应莫名更困难。合并原有移动限制，不覆盖受伤、负重等状态。

提供自由观察模式、自动后退开关及镜头反馈强度。菜单和聊天期间不读取钓鱼鼠标增量。以角色碰撞系统处理岸边、墙体和台阶，禁止直接修改 Transform 穿墙。

鼠标移动不能无限持续：采用反复抬竿、送竿收线的操作循环，并提供暂时释放控竿以重置鼠标位置的方式。测试不同帧率、鼠标灵敏度下的操作一致性。

### D：真实场景与反馈

分为功能表现和正式资产两轮。功能轮使用程序化竿、线、漂、简易鱼体，把因果关系看清；正式轮制作或合法复用竿模型、浮漂、鱼模型、材质及手部动作，并记录来源。

- 竿弯由 B 的负载驱动；鱼线松弛下垂，受力时绷直，竿尖与线起点连续。
- 浮漂实际放在水面世界坐标，保持可读性；避免水材质遮挡、远距离闪烁和不合理放大。
- 鱼体、尾摆、转向和水花对应模拟位置与事件；鱼冲刺时才出现相应强度的反馈。
- 镜头扰动要克制，允许关闭；利用卷线器泄力声、鱼线声和水声表达力量。
- 开发张力 HUD 可切换，最终默认主要通过漂、竿和声音读状态。
- 至少完成一个白天和一个低光条件下的实机场景检查，记录分辨率、视距和性能。

如果缺 Unity 工具、素材或动画编辑能力，交付具体缺口及可导入资源规范；不得把程序化占位杆描述成正式完成的真实持竿动画。

### E：内容与平衡

第一轮只做一根竿、一套线漂钩参数、一种饵、一种鱼和一种料理。命名统一加 `pzaecFishing` 前缀，具体 ID 经 A 写入契约。

参数文件覆盖鱼质量、基础拉力、爆发力、恢复、警觉性、竿刚度、线强度、泄力范围和浮漂浮力。E 负责配置格式和默认配置，B 提供物理参数语义，双方通过交接文档协商，不互改源码。

基于当前整合环境校验配方、图标、中文描述及物品可获取性。界面描述讲清操作和用途，不出现内部类名等实现细节。

后续增加鱼种、体型、天气/时段偏好、图鉴及战利品；这些扩展不得推迟第一套可玩的流程。鱼重量先用于模拟和结果显示，若要随物品交易持久保存，需先验证物品实例元数据接口。

### F：验证、性能与多人

从契约建立风险与验收矩阵，不凭编译成功推断体验完成。独立回放输入，验证跨模块单位、坐标和调用顺序。

多人由服务器权威维护鱼战、饵消耗和奖励；客户端负责及时的竿/漂表现及必要预测。不得信任客户端上传的成功、鱼重或奖励物品。人物移动遵循游戏本身的网络所有权，并由服务器验证位移合理性，不能擅自叠加第二套角色网络控制。

协议需处理版本不符、过期输入、重复包、乱序、超时、断线与重连。限制单玩家活动会话数、消息频率和输入范围。观察者看到的鱼竿、漂和鱼有明确的同步范围。

至少验证单人、主机玩家、远端客户端、专用服务器四条路径；服务器无图形环境不得初始化渲染对象。模拟网络延迟与丢包时，避免张力校正导致无预兆断线，记录校正策略。

性能记录主线程耗时、每帧分配和渲染开销，对比关闭钓鱼、单人钓鱼及多人同时钓鱼。测试报告标明已执行、失败、未执行及原因。

| 里程碑 | 通过标准 |

| M0 技术验证 | A 提交真实接口证据，能检测水面、接管/恢复输入、用角色移动流程试验后退，并发布可编译契约 v1 |

## 7. 多会话协作规则

1. 先让 A 完成 M0 并发布契约 v1，再启动其他会话的实现工作。D/E/F 可以提前做只读调查与方案。
2. 所有会话先读本计划、契约及自己的交接文件，检查工作区变化。当前已有其他模组的未提交修改，不属于本项目。
3. 同一目录并行时禁止切分支、reset、clean、stash、回滚他人改动或全目录格式化。不要执行 `git add .`。仅编辑分配给自己的目录。
4. 不修改其他模组来迁就钓鱼。发现必要兼容改动，交给 A 评估并限定范围。
5. 契约、工程文件、入口和最终 DLL 只有 A 修改。其他会话提出接口变更请求，不自行增加不一致字段或互相调用内部类。
6. B/C/D/E/F 的测试产物写入各自 `tools/Fishing/<模块>/artifacts/`，绝不覆盖模组根目录 DLL。整体构建、安装和游戏重启只由 A 负责。
7. 每个会话交接包含：完成内容、修改文件、公共接口、执行过的命令及结果、未验证项、依赖/阻塞、下一步。编译、独立测试、游戏内实测分别标明。

9. 若采用独立 worktree，由 A 明确创建与合并策略，并配置同一份只读游戏程序集路径；不要照搬相对 HintPath 后假设一定能编译。默认采用同工作区分目录协作。
