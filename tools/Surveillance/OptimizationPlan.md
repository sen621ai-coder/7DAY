# 四路基地监控优化实施方案

日期：2026-09-28。依据：本地 1.0.1 源码审计。实施状态：1.0.2已交付核心优化、试验性自动保底和诊断工具；离线行为测试与原生启动检查通过。客户端画面、GPU性能和实际呈现延迟仍待实测，详见[验证记录](OptimizationValidation.md)。下文参数保留为验收目标，不代表已达标数据。

## 1. 目标与边界

保留每客户端最多四路不同摄像头同时显示、同镜头多屏共享、无线绑定、各自供电及原有存档。优化重点是减少无人观看时的绘制、控制四路同时观看成本，并保证门口目标移动和开关门可及时辨认。

正常四路观看的起始配置：主看镜头目标10次/秒，其余三路各5次/秒，合计最多25次额外场景绘制/秒；没有明确主看屏幕时四路各6次/秒，合计24次。每个游戏帧最多绘制一路。这里的频率是调度目标，实际频率受游戏帧率和单次绘制成本限制。

正常画面不采用低于5次/秒的自动降级档；机器无法维持时明确显示性能受限。对持续不到20 FPS的游戏客户端，一帧最多绘制一路就无法保证四路各5次/秒，不能同时承诺四路最低刷新率和低主视角开销。

视频取自观看客户端已同步、已加载的场景，没有视频编码或网络视频传输。优化降低的是本地额外绘制和等待成本；网络延迟、服务器实体同步、区块和模型加载仍会影响结果。

## 2. 当前代码审计结果

| 当前路径 | 已有行为 / 问题 | 对应措施 |
| --- | --- | --- |
| SurveillanceRenderService.Tick | 距离主格10格内就参加渲染，无正反面和主相机视锥判断 | 用屏面实际位置、正面和主相机视锥筛选 |
| Tick中的renderCursor | 仅检查当前一路，未到时间就不找其他到期镜头；列表按距离排序会变 | 改为按稳定GUID管理的到期时间调度，每帧检查所有到期流 |
| Acquire | 每路固定768×576；相机在首次成功Render前纹理已分配 | 投影尺寸分档；只有首帧成功后才显示画面 |
| Render/Show | LastRender仅成功后更新，但Show不验证帧龄 | 画面超时标记、停止展示过期画面、失败重试退避 |
| Tick/Render/Show | 每帧多个ToArray、LINQ、Tuple、List；反复写相同材质和文字 | 复用集合、缓存查找和组件、仅更新改变的显示状态 |
| streams按GUID共享 | 同镜头多屏只生成一路画面 | 保留；合并需求取可见屏幕的最高画质及刷新频率 |
| 5秒释放 | 停看后延迟释放，但没有全局闲置缓存上限 | 保留5秒热缓存，增加总数上限 |
| ModApi.Update / Client.Receive | 状态快照约2秒；设备查找为枚举 | 视频调度独立于心跳；客户端建立GUID索引，记录快照新鲜度 |

以上从本地源码得出，并非CPU/GPU性能实测结论。不能把2秒设备快照间隔解释成每帧视频延迟。

## 3. 观看判定：先停止无用绘制

1. 使用本地玩家实际世界主相机，不能用监控相机或原生预览相机作为观察者。实施时核对当前游戏的相机取得接口。
2. 以屏面的Transform、尺寸及朝向计算正面、视锥相交和到屏面最近点的距离；不能仅用主格点，以免4×3大屏边缘误判。浮动原点下统一使用Unity渲染坐标。
3. 8格内进入观看，已经观看的屏幕离开10格后退出。背面不申请视频；视锥外持续200ms后停止绘制，回到视野立即加入调度，不额外等待200ms。
4. 屏幕部分进入视野即可参与；屏幕投影跨近裁剪面时保守保留。避免只判断屏幕中心导致画面边缘黑屏。
5. 判定每个游戏帧执行，但只对距离内候选做投影；使用复用的集合和视锥数据，不创建逐帧临时对象。电力/设备状态较慢检查为100ms一次，确认失效后立即撤下画面。
6. 一路只要还有任一可见屏幕需要，就继续渲染。背对全部屏幕200ms后，成功Render调用数应降为0。

首轮不采用墙体射线遮挡作为硬停播条件：单根射线会把门框、栏杆或屏幕自身误认为完全遮挡。隔墙但仍在视锥中的屏幕可能保留部分开销；多点遮挡只能作为后续独立验收项目。也不使用Renderer.isVisible作为唯一依据，因为其他相机也会影响它。

## 4. 按实际显示尺寸分配分辨率

以屏面四角在玩家视口中的投影估算像素高度，保持4:3比例。比纯距离分档更能适应不同显示器分辨率、视野角度和斜看屏幕。

| 投影像素高度初始阈值 | 请求纹理 | 用途 |
| --- | --- | --- |
| ≥480像素 | 768×576 | 近看、门口细节 |
| 240～479像素 | 512×384 | 常规观看 |
| <240像素 | 384×288 | 较小的远处/侧面屏幕 |

阈值上下各保留约15%回差；降档条件连续满足1秒，升档条件满足300ms。通常每路最多每2秒重建一次纹理；玩家明确切换到近看焦点可提前升档一次，随后进入冷却。

同一摄像头被多个可见屏幕使用时，采用它们要求的最高档位，仍共用一路；不可见屏幕不抬高画质。只有分辨率或数据真正改变时才重绑材质，避免反复更新TextMesh和状态字符串。

尺寸切换时先生成新纹理的有效首帧，再切换所有共享屏幕并释放旧纹理。首次进入和改频道显示“正在连接”，不能展示未初始化纹理或将旧频道帧配上新频道名称。换纹理也占用每帧一次的绘制额度。

512×384像素数是768×576的约44%，384×288约25%；这只说明纹理和像素绘制规模，不代表完整场景渲染耗时会同比减少。

## 5. 刷新调度：保障每路及时更新

### 5.1 正常目标

| 可见独立镜头数 | 目标频率 | 每秒额外绘制总数 |
| --- | --- | --- |
| 1路 | 10Hz | 10 |
| 2路 | 各10Hz | 20 |
| 3～4路，有明确主看镜头 | 主看10Hz，其余各5Hz | 20～25 |
| 3～4路，无明确主看镜头 | 各6Hz | 18～24 |

主看定义：屏面包含主相机视口中心；多个重叠时优先更近者，焦点变化稳定300ms才切换。仅打开菜单不代表后台不可见屏幕要保持高刷新。超过四路时优先主看、再按可见投影面积和距离选取；边界竞争至少稳定500ms，避免走动时名额不断跳换。

### 5.2 调度规则

- 每路保存GUID、LastSuccessfulRender、NextDue和FirstFramePending。每个游戏帧从所有到期流中选择最早到期者；相同时按稳定顺序轮换。不同频率通过不同NextDue体现，不能每帧只选焦点流。
- 新唤醒或切频道可以得到一个首帧优先机会；已有画面接近超时阈值时先补该路。每路的首帧优先请求合并，连续切频道不得饿死其他三路。
- 每个游戏帧最多一次Camera.Render。成功后NextDue=当前时间+目标间隔，不补绘积压历史帧；低帧率时调度自然放缓，不在恢复后集中补帧。
- 不使用与门口是否检测到目标相关的停播规则。静止、缓慢移动或未触发传感器的目标仍需可见。
- 无需为每个已绑定频道创建相机，只有正在观看的频道参加调度。轮巡沿用5秒，只为新频道请求首帧。

这些规则降低队头等待和同帧尖峰，但Camera.Render本身不能中途暂停；昂贵的单次场景绘制仍需通过实测与画质调节处理。

## 6. 延迟、恢复与失败状态

把三个指标分开记录：A为客户端场景发生变化到被下一次监控采样的等待；B为采样到屏面被主相机实际呈现的耗时；C为真实服务器事件到客户端状态到达的耗时。A+B是本方案要控制的本地附加延迟，C需联机另测。

10Hz理想采样等待为0～100ms，5Hz为0～200ms，均另加主相机帧边界及绘制/显示时间。这不是保证的端到端延迟。以下是游戏实际维持≥30 FPS、区域已加载、网络状态正常时的验收目标：

| 指标 | 初始验收目标 |
| --- | --- |
| 主看一路本地附加延迟 | p95 ≤200ms |
| 其他可见镜头本地附加延迟 | p95 ≤300ms |
| 缓存有效时重新看向一块屏幕 | 有效新帧p95 ≤250ms |
| 同时重新看向四块屏幕 | 全部有效新帧p95 ≤400ms |
| 新建相机/手动换频道 | 场景与配置就绪后首帧p95 ≤500ms |
| 退出观看 | 最迟约200ms加一个游戏帧停止绘制 |

客户端卡顿、切频道的网络往返和区块未加载时不应伪装成满足上述目标；分别记录等待原因。服务端配置确认前保留旧频道的正确标签；确认切换后显示连接中，直至新频道帧成功。

LastSuccessfulRender只在成功绘制后更新。可见画面超过300ms未成功更新，显示“画面延迟”与帧龄；超过500ms撤下旧帧，显示“连接中断/性能受限”。已知断电、镜头卸载或拆除时立即显示对应状态，不等500ms。再次唤醒不显示缓存的过期帧冒充实时画面。

连续渲染异常使用100ms、250ms、500ms上限的重试退避，并限频日志；失败流不能占住所有调度机会。重新连接后先成功绘制再恢复正常显示。远端快照超过6秒未更新应标记状态同步异常；新增帧龄检查不能证明摄像头远景、实体或网络数据本身完整，仍需场景实测。

## 7. 性能不足时的降级规则

先上线可解释的固定规则，再凭测量启用自适应。自适应开关默认为保守，使用总帧时间、实测绘制调用耗时、有效刷新率和帧龄；CPU端Camera.Render计时不能代表GPU成本。若本机拿不到有效GPU计时，不伪造GPU预算达标数据。

以30 FPS（33.3ms）作为初始保底目标。连续2秒总帧时间偏高或有效刷新率达不到目标时，只降一档并观察至少2秒：

1. 非主看镜头纹理先降低一档，最低384×288。
2. 主看镜头降到512×384，优先保留10Hz。
3. 如仍不足，主看也降到5Hz，其他镜头最低维持5Hz；非主看6Hz档改5Hz。
4. 仍无法达标时显示性能受限和实际刷新率；如有旧帧超过500ms，按失效规则撤下。用户可选择仅保留重点镜头或改为轮巡，不能自动隐藏问题并宣称四路实时。

稳定有余量10秒后一次只恢复一档；焦点变化不重置所有镜头质量。自适应需有手动“固定标准”覆盖项，便于用户排查和做同场景对比。与监控无关的主场景重负载也可能触发保底，因此它是保护机制，不是瓶颈归因工具。

首轮不自动缩短80格裁剪距离，以免门外目标被裁掉；不全局修改游戏阴影/LOD。关闭监控相机后处理、调整相机专用阴影等作为第二轮实验，先核查ElectricityCamera组件及本游戏管线支持，验证夜间、雨雾、门遮挡和僵尸可见性后才选用。

## 8. 资源与维护成本

- 活跃不同镜头最多4路；闲置热缓存最多4路且最长5秒，总相机/常驻纹理最多8路。超出先释放最久未使用的闲置流，活跃资源不能被缓存挤出。
- 分辨率切换允许一张临时替换纹理；切换完成立即释放旧纹理，失败销毁新纹理。每帧最多处理一个重建，避免切四路时集中分配。
- 退出世界、断线、设备模型失效要撤销引用，切世界必须清空缓存。重复进入观看20次后对象数不能单调增长。
- 将活跃列表、排序缓冲、反馈屏面临时隐藏列表改为复用集合；缓存TextMesh Renderer和摄像头GUID索引。按变化更新文字/材质，渲染期间屏面隐藏与恢复仍保留finally保护。
- 模块稳定运行时逐帧托管分配目标接近0；记录该模块分配来源，不能以整个游戏仍有GC判定优化无效。状态变化和纹理重建的分配单独统计。

## 9. 开发顺序和验收

### 第一阶段：测量与正确性

增加可关闭的诊断：活跃/缓存流数、各路目标与实际Hz、帧龄、唤醒/首帧耗时、纹理尺寸、渲染失败数、Camera.Render CPU调用耗时、总帧时间。运行中累计，每秒聚合一次，结束导出；避免逐帧写磁盘。

先修正到期调度、首次有效帧、500ms过期撤帧及资源上限，再加入主相机观看筛选与复用集合。离线调度测试覆盖四路公平、不同频率、连续切换不饿死、低FPS不补帧及失败重试不独占；视锥/模型/呈现仍用真实图形客户端测试。

### 第二阶段：画质与保底

加入投影尺寸分档、分辨率切换回差、焦点10Hz与旁路5Hz档位。达到验收目标后再启用自适应，不通过就保留固定标准档并记录未达标项目。

### 测试矩阵

同一基地、同一玩家位置及镜头方向，固定游戏画质和输出分辨率，预热30秒；每组录制60秒，至少重复3次，并交替测试顺序。记录当前1.0.1和优化版，不以专用服务器启动日志替代客户端数据。

| 场景 | 必验项目 |
| --- | --- |
| 无监控绘制 / 1路 / 4路，正面观看 | CPU/GPU可用指标、总帧时间中位数和p95、各路有效Hz和附加延迟 |
| 4路背对，再迅速转身 | 停绘时间、恢复首帧、无旧图伪装/未初始化纹理 |
| 4屏共用1镜头 | 只有1个活跃流；近看需求抬高共享质量，远屏不额外复制相机 |
| 门外移动僵尸与开关门 | 可识别接近方向和门状态，画面有正确遮挡；必要时用已加载场景里的受控门事件测本地附加延迟 |
| 地下16/32格，地面门口水平16/48格 | 地形、僵尸和光照完整；玩家不移动到室外也能观看 |
| 四个屏幕来回扫视、频道轮巡 | 无频道标签错配、无频繁纹理重建、非主看镜头不饿死 |
| 30/60 FPS及重负载、夜间、雨雾 | 记录画质变化、延迟和主游戏帧时间，不能仅测白天空场景 |
| 断电、卸载、渲染异常、远端掉线 | 明确失效状态，旧帧超时撤下；恢复后重新取有效帧 |
| 两个客户端 | 本地观看调度彼此独立，不改变对方频道、画质或渲染额度 |
| 重复启停20次、切世界 | 资源受控；停看5秒后清理，退出世界全部释放 |

量化目标：四路常规观看时，总帧时间中位数相对同场景禁用额外监控绘制增加≤15%、p95增加≤20%；同时满足本节延迟和最低刷新率。此为待测验收线，并非当前性能承诺。若1.0.1已经低于这条线，还需对比优化版不因管理逻辑而回退。

本地附加延迟测量优先使用调试夹具：在已加载监控场景中按已知单调时间改变一个可见状态，同时记录事件与成功采样时刻，再通过客户端录屏/帧捕获核对实际屏面呈现。采样日志只能测A，不能独自证明A+B。真实服务器事件的端到端延迟在远端客户端单独记录，包含网络影响。

## 10. 交付方式

实施时修改SurveillanceRenderService.cs、ScreenModel.cs；按诊断/索引需要小改SurveillanceProtocol.cs和ModApi.cs。先在独立测试目录保存1.0.1 DLL备份，优化版提升ModInfo和启动日志版本，重编译DLL，更新README与对应测试。保留原有绑定和存档格式。

首轮代码已落实：公平到期调度、只渲染正在看的屏幕、10/5Hz分配、投影分辨率分档、过期画面保护和有上限的热缓存。自动保底作为可选试验功能默认关闭；真实客户端延迟与场景可用性按验证记录继续验收。
