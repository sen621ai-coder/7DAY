# 自动林场全链路复盘（2026-09-21，v4）

## 结论与证据边界

正常创建、区块卸载复用、原生采集器数据读取的主链路成立；失败隔离、资源所有权、已损坏实例的恢复仍不完整。v4 是针对对象池清理共享材质的防护，不能把它当作双方延迟变紫的唯一根因已经实测确认。

已检查当前 C#、XML 和本机 Assembly-CSharp.dll 的 IL。最新可读日志为 2026-09-20 23:02:55 的会话，记录的是 v2；没有 v4 持续联机实测证据。该会话使用 Intel Arc Pro、Direct3D11 功能级别 11.1，原生材质为 woodWorkBench，着色器 Game/Entity Tint Mask。模型创建成功；期间约每 20 分钟清理资源，但没有变紫发生时的材质实例记录，不能据时间邻近认定清理就是原因。

## 各阶段

| 阶段 | 当前逻辑 | 复盘结果 |
|---|---|---|
| 启动 | T16RuntimeFixMod.InitMod 顺序安装其他补丁、采集器补丁和林场补丁 | 林场异常会进入外层共同 catch，后续其他系统的安装被跳过；缺少局部失败隔离 |
| 资源定位 | 从 99 的目录相对定位 98/Resources/Forestry | 双方必须安装资源；启动只检查 sawmill.meshbin，贴图和远景文件延后检查 |
| 首次取模型 | 拦截 BlockShapeModelEntity.getPrefab，限定方块名和 Model 字符串 | 普通模型不受影响；缓存存在后不会再验证材质、贴图、网格 |
| 创建 | 停用的 DontDestroyOnLoad 缓存根节点；生成网格、碰撞、材质、木工设备、库存与 LOD | 主体顶点和索引有验证；碰撞体通过 RootTransformRefParent 指向模型根；零 Y 偏移和底座匹配 |
| 创建失败 | catch 销毁缓存 GameObject 后重抛 | 没有跟踪并销毁已创建的 Mesh、Material、Texture；没有集中失败清单、重试间隔或替代显示 |
| 放置预览 | 原生 CloneModel 直接 Instantiate(getPrefab()) | 不经过采集器动画 Bind；原生染色/位置/旋转流程保留。直接克隆和对象池取出是两条路径，不能混为一谈 |
| 区块加载 | 原生对象池创建或取回实例，注册 BlockEntityData；激活前执行采集器回调 | 原生 PoolItem.Instantiate 只改名，不加包装根；v4 标记组件应跟随克隆，根匹配逻辑成立 |
| 动画绑定 | 找 MachineryNear 所在 LOD 根，添加或复用 Activity，Initialize、Reset、Bind | 正常实例重新绑定新的 world/位置；初始化成功后才置 initialized，避免半初始化被当成功 |
| 等待同步 | 每 0.5 秒读原生 TileEntityCollector；没有实体或 Items 时保持等待 | 不写生产、燃料或网络数据。原生 isDisabled 的字典读取使用 TryGetValue，缺失状态不会仅因缺 key 抛异常 |
| 运行 | 按燃料/库存/插件状态展示木堆、灯光和机械 | 只读显示与生产账目分离；Update/Poll 缺少异常边界，配置缺项或对象失效仍可能反复报错 |
| 普通卸载入池 | 原生先 SetActive(false)，Activity.OnDisable 清空绑定并重置外观 | 重入池后不再轮询旧世界；正常再次取出时由激活回调重新 Bind |
| 真正销毁 | v4 在 GameObjectPool.DestroyObject 前清空该林场实例的 Renderer 材质引用 | 原生随后无法从这个实例取得共享材质去销毁；不跳过原生对象销毁，不修改其他方块 |
| 退出/重进 | 原生回收世界实例；自定义 prefab 缓存跨场景保留 | 是进程级复用，不是每个世界重新创建。切服后不同模型模式共用一个静态缓存，有尺寸沿用风险 |
| 已损坏材质恢复 | 木堆初始化可重新取得 timberMaterial；其他材质没有统一恢复 | GetPrefab 只判根对象是否存在；旧根仍有效但材质失效时不会重建。initialized=true 的实例再 Bind 也跳过初始化 |

## 按优先级列出的缺口

### P1：显示恢复缺少完整链路

AutoForestryModel.GetPrefab（约第 47 行）只检查 prefab 是否为 null；GetTimberMaterial（约第 124 行）只解决木堆原材质；AutoForestryActivity.Initialize（约第 68 行）在 initialized 后直接返回。缓存网格/材质/纹理部分失效时，不会自动发现并恢复整栋建筑，也不能仅重建缓存就修复已经加载的实例。

建议：建立资源代次和绑定表，记录每个 Renderer 应使用的材质；低频验证共享资源，重建后同时更新缓存与活跃实例。先记录缺失对象类别，不要在每帧盲目重建或改写共享资源。

### P1：启动失败会影响后续系统

T16RuntimeFixMod.InitMod 第 27 行在共同 try 内安装林场。缺少主网格、方法匹配失败等会跳到共同 catch，后续安装不会执行。林场 Install 也可能已经安装部分 Harmony 补丁后失败。

建议：先预检完整资源及补丁目标，再独立安装；失败日志应明确林场不可用，其他不依赖林场的系统仍继续启动。不能静默吞错冒充成功。

### P2：动画失败缺少本次区块内的重试

Activated 的 catch 会停用 Activity 并清除绑定；这避免阻断建筑激活，但没有定时重试。本次区块停留期间，即使问题消失也不会恢复，通常需要区块重载触发下一次 Bind。

建议：保存待绑定上下文，有限次数、带间隔地重试；日志去重。运行时 Poll/Update 同样需要受控降级，保持原生交互和生产不受动画错误影响。

### P2：资源分配失败没有完整回滚

CreatePrefab 失败只 Destroy(cache)。运行时创建的 Mesh、Material、Texture 属于独立 Unity 对象，并不等于销毁 GameObject 就显式释放；后续依赖引擎回收，反复失败可能累计分配。timberMaterial 也可能跨失败保留。

建议：区分借用的原生资源和本模型创建的资源；创建成功后转交缓存持有，失败时只释放本次自有资源，避免误销毁游戏原生资源。

### P2：同进程切换模型模式会复用首次尺寸

缓存只有一份。Compact 缩放仅发生在第一次创建后；连接另一个使用不同模式的服务器但不退出客户端时，返回的缓存可能仍是上一模式的尺寸。现有模式切换脚本要求先关游戏，降低本机切换风险，但不等价于覆盖所有切服场景。

### P3：历史残留和材质表现限制

- 木堆已改为直接显隐，但仍创建、保存、销毁 fadeLog，并创建未使用的 logProperties，徒增所有权复杂度。
- 创建阶段已不再启用 Standard 的法线、金属、透明关键字。原生 Entity Tint Mask 是否消费所有指定贴图，离线渲染不能证明；不能宣称细节表现完全等同原 Standard 方案。
- 部分初始化节点缺失会静默跳过；应在开发诊断中记录必需节点完整性。

## v4 回收保护能证明什么

已从原生 IL 确认：DestroyObject 调用 CleanupMaterialsOfRenderers；后者将取到的运行时材质（负 InstanceID）交给 Object.Destroy。林场共享运行时材质不适合由单个实例回收路径销毁，v4 在这个入口解除引用的方向正确。

但原生 PoolObject 通常先停用整个对象；DestroyObject 使用默认不包含停用子节点的 GetComponentsInChildren。林场根本身没有 Renderer，因此某些回收场景可能根本没有收集到材质。现有离线测试模拟了销毁材质和停用子节点保护，却不是真实 Unity 的活动层级遍历，也不包含真正的帧末 Destroy。此前“确定就是这次紫色唯一根因”的表述过强，应予以更正。

## 本次验证

- 实际模型构建代码经离线适配器导出：134 个 Renderer、16 个材质、33,637 个三角形；碰撞根引用、原生着色器选择、辅助纹理保留通过。
- v4 回收前解除材质引用：重复实例、停用子节点、其他方块不受影响的模拟检查通过。
- 空材质恢复、原生状态读取策略、40,002 个机械循环采样检查通过。
- 采集器批量产出、燃料、满仓、插件降级保存、林场 XML/网格/贴图检查通过。
- 同一个 PowerShell 进程连续运行独立测试曾因重复 Add-Type 名称失败；分进程重跑通过。这是测试宿主冲突，不是游戏运行失败。
- 本次仅复盘并输出报告，没有修改或安装生产代码。

## 推荐下一轮验证顺序

1. 加入资源诊断：模型代次、材质/Shader/贴图实例 ID、有效性、实例创建/入池/销毁计数；只在状态变化时记录。
2. 补齐启动局部失败隔离、创建回滚、动画有限重试及资源重新绑定。
3. 双机同版本，记录刚进服、放置/取消、拆除一个保留另一个、离开区块返回、退出重进的结果。
4. 持续运行跨至少两轮约 20 分钟资源清理，并记录首次变紫的时间、近/远 LOD 和双方日志。
5. 独立验证专用服务器无图形环境、资源缺失/坏文件、同进程切服；这些不能由当前离线测试代替。
